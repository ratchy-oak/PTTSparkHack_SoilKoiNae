## สิ่งที่ทำแล้ว

- `/` และ `/office` เป็น dashboard แผนที่แบบลาก/ซูมจริงด้วย Leaflet / OpenStreetMap
- ข้อมูลสาธิต 8 จุด สี่สถานะ ค้นหา กรอง กดหมุด/รายการเพื่อดูรายละเอียด
- ค่าดิน 4 รายการ กราฟ 6/24 ชั่วโมง แบตเตอรี่ สัญญาณ และเวลาวัด
- หมุดสีเขียว = อยู่ในช่วงทดลอง, ส้ม = เฝ้าระวัง, แดง = นอกช่วง, ดำ = ข้อมูลหาย/อุปกรณ์มีปัญหา
- หมุดทุกสีมีสัญลักษณ์และข้อความ ไม่อาศัยสีเพียงอย่างเดียว
- หน้าแผนที่เดียวพร้อมรายการจุดตรวจ ส่งออก CSV ตามตัวกรอง และหน้าต่างดูเกณฑ์
- แยกโหมดข้อมูลตัวอย่างออกจากอุปกรณ์จริง ไม่เพิ่มข้อมูลสมมติลง Supabase
- `/api/soil/ingest` รับข้อมูล JSON จาก Gateway ที่ยืนยัน token แล้วเท่านั้น
- migration แยกโดเมน Soil พร้อม RLS, staff read-only, deduplication `(device_id, at)`
- migration ยังไม่ได้ติดตั้งบนฐานข้อมูลจริง; ไม่มีฮาร์ดแวร์เชื่อมจริงในงานนี้
- ซอร์ส LINE/ICS และไฟล์ทดสอบเดิมถูกนำออกแล้ว เก็บ migration เดิมไว้สำหรับประวัติฐานข้อมูลและบัญชีเจ้าหน้าที่

## ข้อเสนอฮาร์ดแวร์รุ่นแรก (ยังไม่ได้ผลิตหรือทดสอบ)

1. หัววัด pH แบบใช้ในดินได้จริง พร้อมวิธีเตรียมดิน/สอบเทียบที่ผู้ผลิตระบุ
2. หัววัด EC ต้องระบุว่าเป็น bulk/apparent EC หรือสารละลาย และหน่วย mS/cm ค่าเกลือจาก lab ECe เทียบตรงกับหัววัดทุกแบบไม่ได้
3. ความชื้น VWC ต้องสอบเทียบกับดินพื้นที่ ไม่ใช้เปอร์เซ็นต์จาก ADC โดยไม่มีการสอบเทียบ
4. อุณหภูมิดิน บันทึกความลึกและตำแหน่งติดตั้ง
5. MCU / RS485 ตามรุ่นหัววัด, ตรวจ battery voltage, watchdog, กล่องกันน้ำ, สายและขั้วต่อเหมาะกับน้ำท่วม
6. Solar + battery ขนาดตาม power budget ที่วัดจริง มีวงจรป้องกันแบตเตอรี่
7. LoRaWAN ผ่าน Gateway หรือ cellular ตามการสำรวจสัญญาณ ไม่อ้างระยะส่งก่อนทดสอบ
8. เก็บข้อมูลค้างส่งเมื่อไม่มีเครือข่าย โดยเก็บเวลาวัดเดิมและป้องกันรายการซ้ำ

อย่าอ้างว่า NPK แบบราคาถูกตรวจธาตุอาหารได้แม่นยำ หรือ pH/EC ตรวจยาฆ่าแมลง/โลหะหนักได้ ต้องใช้วิธีเฉพาะและผลห้องปฏิบัติการที่เหมาะสม ขณะนี้ยังไม่เลือกรุ่น/BOM/ราคา

## เปิดต้นแบบ

```sh
npm install
npm run dev
```

เปิด http://127.0.0.1:3000 ข้อมูลตัวอย่างทำงานได้โดยไม่เขียนฐานข้อมูลจริง พิกัดเป็นตำแหน่งสมมติแถวพื้นที่เป้าหมาย ไม่ใช่แปลงของเกษตรกรจริง แผนที่พื้นฐานต้องใช้อินเทอร์เน็ต เมื่อโหลดพื้นแผนที่ไม่ได้ยังเลือกจุดจากรายการได้

## เชื่อมข้อมูลจริง

1. ตรวจและติดตั้ง `supabase/migrations/202610200009_soil_monitoring.sql` บนโปรเจกต์ที่ต้องการ (ยังไม่ได้ทำให้อัตโนมัติ)
2. ลงทะเบียนอุปกรณ์ใน `soil_devices` ด้วยผู้ดูแลฐานข้อมูล ชื่อ/พิกัดต้องตรงกับจุดติดตั้งจริง
3. สร้าง random secret อย่างน้อย 32 ตัวอักษร ตั้ง `SOIL_INGEST_TOKEN` ฝั่งเซิร์ฟเวอร์และ Gateway เท่านั้น พร้อม Supabase URL และ service key เดิม ห้ามใช้ NEXT_PUBLIC_ กับ token
4. Gateway ส่ง HTTPS POST `/api/soil/ingest` พร้อม `Authorization: Bearer <secret>` และ `Content-Type: application/json`
5. เข้าสู่ระบบบัญชีเจ้าหน้าที่เดิมผ่าน `/login` แล้วเลือกโหมด “อุปกรณ์จริง” หน้า dashboard โหลดใหม่ทุก 1 นาที ข้อมูลไม่เกิน 300 readings ล่าสุดต่อจุด กราฟตามเวลาวัดจริง
6. ก่อน deploy ต้องเลือก hosting/TLS, rate limit ที่ gateway/edge, token rotation, observability, retention และ tile provider ให้เหมาะกับจำนวนผู้ใช้ OSM public tiles ไม่ใช่บริการพร้อม SLA และห้าม bulk/offline prefetch

ตัวอย่าง payload (ค่าตัวอย่าง ต้องเปลี่ยน `at` เป็นเวลาวัดจริง):

```json
{
  "device_id": "SQ-001",
  "at": "2026-10-20T06:00:00Z",
  "ph": 6.3,
  "ec": 0.82,
  "moisture": 42,
  "temperature": 28.4,
  "battery": 91,
  "signal": -73,
  "fault": null
}
```

ทุก field ต้องส่งมา ค่าเซ็นเซอร์ที่หายใช้ null พร้อม fault code ถ้ามี ห้ามแทนค่าหายด้วย 0 เวลาเป็น ISO8601 ที่มี timezone รับย้อนหลังไม่เกิน 7 วัน/อนาคตไม่เกิน 5 นาที JSON ไม่เกิน 8 KB คำขอซ้ำไม่เปลี่ยนค่าที่บันทึกแล้ว

สถานะ HTTP: 201 บันทึกใหม่ / 200 ซ้ำ / 400 payload ผิด / 401 token ผิด / 404 อุปกรณ์ไม่พบหรือปิดใช้งาน / 413 ใหญ่เกิน / 415 content type ผิด / 503 ยังไม่ตั้งค่าหรือฐานข้อมูลไม่พร้อม

## ก่อนใช้เกณฑ์จริง

- ยืนยันพืช ระยะปลูก ลักษณะดิน และระดับน้ำในนา: moisture ของดินอิ่มน้ำใช้ threshold เดียวกับดินแห้งไม่ได้
- เปรียบเทียบผลกับเครื่องอ้างอิง/ห้อง lab หลายสภาพ ไม่สรุปจาก sample เดียว
- กำหนด error budget, ความลึกหัววัด, รอบสอบเทียบ, offline timeout ตามรอบส่งจริง
- ใช้หลายจุดและ sampling plan ที่เหมาะสม: จุดเดียวไม่ใช่ตัวแทนทั้งแปลงเสมอ
- ทดลองกับเกษตรกรและผู้ตรวจ วัดเวลาค้นจุดผิดปกติ ความเข้าใจสี false alert และเวลาแก้ปัญหา
- เมื่อ profile ผ่านการยืนยัน ควรจัดเก็บ version, ผู้อนุมัติ, วันเริ่มใช้ และบันทึกค่าที่ใช้ประเมินย้อนหลัง ก่อนเปิดใช้งานจริง
